# HTSDesk full-stack audit — 27 September 2026

Five independent line-by-line reviews (security, calculation engine, frontend/UX,
DevOps/infrastructure, test-strategy/QA), each reading source directly rather than
trusting `docs/STATUS.md` or the earlier audit docs. Every claim below was verified
against the current tree; where an earlier doc's claim held up it is marked
confirmed, where it didn't it is marked stale. No production data was touched.

**Baseline:** working tree as of commit `915cb6c`. This report describes
findings as of that baseline; fixes applied afterward are noted below rather
than rewritten into the findings themselves.

## Verdict

The engineering is genuinely good in the parts that were built to be checked:
money math is exact-Decimal and property-tested, SQL is parameterized and
account-scoped everywhere, the two previously-fixed races (API rate limiter,
credential throttle) are real atomic fixes, the ingest pipeline's schedule/rules
build is transactional with real floors and rollback, and the uncertainty-first
UI philosophy (`QuoteFigures.tsx`) is unusually disciplined for a pre-launch
product.

The pattern across all five reviews is the same one: **the safety net is
optional, not enforced.** Tests that would catch a specific, previously-real
bug exist and pass, but aren't wired into CI. A confidence gate exists but was
never validated against measured accuracy. A reasoning-layer safeguard exists
only as the absence of an environment variable. A backup procedure exists only
for a database the product isn't actually going to run on. Three test files
carry the exact hazard (writing to `data/accounts.db`) that a past incident
already caused, undetected because nothing distinguishes them from the 24 other
files that were fixed to never do that.

This is not a "rewrite it" verdict. It's a "close the twelve places where a
correct design has a bypass" verdict.

## Cross-cutting: CI enforces roughly a third of what's built

Every review independently arrived at the same number from a different angle:
`.github/workflows/ci.yml` runs `tests/test_duty.py`, `tests/test_classify_eval.py`,
and `npm run test:integration` (10 of ~29 web test files) — about 152 of the
~407 checks that exist in the repo. Everything else (`test_regimes.py`,
`test_api.py`, `test_refresh.py`, `test_adcvd.py`, `test_math.py`,
`test_rate_limiter.py` — the literal regression test for the rate-limiter race
this repo already fixed once — `test_backup_security.py`, every Playwright
browser suite, Google OAuth, reprice/review-race tests) requires a human to run
`make check` by hand before a release, and nothing merges to main gates on it.
`docs/STATUS.md`'s release-gate checkbox "Integration tests exercise production
routes, over isolated databases" is true of 10 files and false of 3 more that
run under the same `make check` umbrella (see Critical #4).

## Findings, in remediation order

### 1. Critical (calculation) — classifier confidence gate lets a wrong heading through as "ready"

`api/main.py:478-484` only routes a line to review when `confidence == "low"`.
`confidence` (`core/classify.py:286-288`) is a heuristic on ruling-vote count
and score, never validated against the measured 48.8% top-1-heading / 15.5%
exact-10-digit accuracy (`grep -n confidence tests/eval_classify.py` returns
nothing). A description-only line that draws 2-3 loosely related ruling votes
(satisfying "medium"/"high") for a wrong heading whose siblings happen to share
one rate returns `status: "ready"` — LINE_STATUSES' own comment says this means
"priced, complete, and nothing to confirm" — with an exact dollar figure and no
review flag. Only two tests assert `status == "ready"` (`tests/test_api.py:388,467`)
and both supply an explicit `hts`; no test exercises description-only classify
→ "ready". This re-opens `docs/PROJECT-AUDIT.md`'s 2026-09-19 finding #14,
half-fixed: `suffix_review` catches sibling-rate divergence but not "is this
even the right heading."

**Fix:** never let a classifier-sourced code reach `ready` without an explicit
human approval, regardless of confidence bucket, until confidence is measured
against `eval_classify.py`'s held-out set and shown to be predictive.

### 2. Critical (calculation) — the reasoning-layer safeguard is an environment accident, not a gate

`core/classify.py:367` defaults `use_reasoning=True`. Both production call
sites (`api/main.py:342`, `api/main.py:419`) never pass `use_reasoning=False`.
The only thing stopping every classify call from making paid reasoning calls
today is `os.environ.get("ANTHROPIC_API_KEY")` being unset on this host
(`api/main.py:240`). If that key ever exists in the API process's environment
for any reason — shared secrets store, someone running
`eval_classify.py --reasoning` on the same venv — every audit line silently
starts making real model calls and returning unmeasured output as
classification, with no code change and no deploy.

**Fix:** flip the default to `False`; gate reasoning behind one explicit,
auditable flag, not env-var presence.

### 3. Critical (calculation) — AD/CVD case-identity check silently passes on unparseable headers

`ingest/adcvd.py:266-278` `_own_case()` returns `None` (not `False`) when a
notice's header doesn't match `_HEADER_CASES` — correct for old-format notices
per its own test fixture (`tests/test_adcvd.py:294,309-311`). But
`_try_candidates` (281-302) only skips on `_own_case(...) is False`; `None`
falls through to acceptance on search rank alone, with zero case-identity
confirmation. `latest_scope()` specifically prefers older, more
historically-formatted notices — exactly where a header miss is likeliest.
This contradicts, rather than confirms, `docs/STATUS.md`'s fix #1 ("a
candidate is only accepted when the case is one of the numbers the Federal
Register brackets"), which is true only when that bracket parses.

**Fix:** treat `None` as fail-closed, matching the module's stated philosophy
everywhere else in it.

### 4. Critical (QA) — three test files can write to `data/accounts.db` in normal use

`web/tests/security.test.mjs`, `authflow.test.mjs`, `journey.test.mjs` import
`helpers.mjs`, which has none of `harness.mjs`'s existing-DB refusal logic
(`harness.mjs:47-60`) — they fire real traffic at whatever's already running at
`localhost:3000`. `web/src/lib/store.ts:17-18` defaults to
`../data/accounts.db` when `HTSDESK_ACCOUNTS_DB` is unset, and `make web` does
not set it. `journey.test.mjs:143-145` POSTs to `/api/admin/diff` — the exact
call that wiped the diff cursor in the incident this repo already had. A
developer who starts the app normally and runs `make test-journey` to sanity-
check a change reproduces that incident with no test-side guard. This is the
one place `docs/RUNBOOK.md`'s blanket claim "no test may touch
`data/accounts.db`" is false.

**Fix:** port these three files onto `harness.mjs`'s `startApp()`/scratch-DB
pattern, or give `helpers.mjs` the same existing-DB refusal.

### 5. Critical (DevOps) — no tested restore path for the database the product will actually run on

`ops/backup-accounts.py`/`restore-accounts.py` only operate on a local SQLite
file. In the decided topology, accounts live in Turso
(`web/src/lib/store.ts:11-20`); neither script can reach a remote libSQL
database. `docs/DEPLOY.md`/`docs/RUNBOOK.md` are honest that recovery is
punted to "Turso's own scheduled backups... enable its scheduled backups on
the database dashboard" — a manual, external, unverified toggle nobody has
evidence of turning on. A bad migration or bug in week one of a real launch has
no rehearsed recovery.

**Fix:** actually rehearse a Turso dump/reload before calling anything
launched, and write down the working commands.

### 6. High (UX/trust) — classify-page confidence badges use the same green as a genuinely complete answer

`src/app/classify/page.tsx:116-126` gives "high confidence" a green
`tone="good"` badge — the same visual language the audit engine reserves for a
complete, reliable duty figure — with only a small gray caveat sentence
competing against it. Elsewhere (`auditModel.ts` STATUSES, `low_confidence`)
the product forces uncertain lines into a "needs review" bucket everywhere;
`/classify`, the first nav item and most likely first thing a new SMB visitor
tries, has no equivalent gating and discloses the measured (low) accuracy
nowhere in the UI. This is the one place the product's otherwise-consistent
honesty-about-uncertainty design doesn't reach — and it compounds Critical #1.

**Fix:** strip the green tone from confidence badges until gated the same way
audit-engine statuses are, or add an equally-weighted, persistent caveat.

### 7. High (security/QA, cross-cutting) — the release-gate test suites aren't a merge gate

Covered under "Cross-cutting" above. Specifically absent from CI despite being
self-contained/skip-safe: `tests/test_rate_limiter.py` (the literal regression
for the already-fixed cross-worker race), `test_backup_security.py`,
`test_math.py`, `test_adcvd.py`, `test_regimes.py`, and on the web side
`security.test.mjs`, `auth-transaction.test.mjs`, `reprice-review-races.test.mjs`,
`catalogue-costs.test.mjs`, `google-auth.test.mjs`. A regression in any of
these ships silently.

**Fix:** add the self-contained Python suites to `ci.yml`'s existing job (zero
new infra); add a nightly/release CI job that installs Chrome and runs
`make check` end-to-end for the rest.

### 8. High (DevOps) — zero monitoring/alerting anywhere

No Sentry/Datadog/uptime-check/`OnFailure=` pattern anywhere in the repo.
`/api/health` (`api/main.py:203-245`) exposes exactly what's needed
(`built_at`, `dataset_revision`) but nothing polls it. A failed 09:00 UTC
ingest is only visible via `journalctl` or a human remembering to check —
worst case, the site silently serves stale tariff data for days.

**Fix:** a free dead-man's-switch ping (e.g. healthchecks.io) on the ingest/diff
timers, plus an external uptime check on `/api/health` alerting on
`status != ok` or a stale `built_at`.

### 9. High (DevOps) — single VPS runs API, ingest, and diff with no scaling/failover story

`deploy/htsdesk-api.service` runs `uvicorn --workers 2` on one box
(`docs/DEPLOY.md:15`). `Restart=always` survives a process crash, not a host
outage. No load balancer, no second instance, no documented capacity plan.

**Fix:** at minimum document the accepted-risk decision explicitly (this may be
fine for launch scale); don't let it be implicit.

### 10. Medium (security) — CSP has no `script-src`, so it does nothing against XSS

`web/next.config.ts` sets `frame-ancestors`/`object-src`/`base-uri` but no
`script-src`. No injection point was found (React escapes everywhere, no
`dangerouslySetInnerHTML`), so urgency is low, but the policy currently
provides no defense-in-depth if one is ever introduced.

**Fix:** add `script-src 'self'` (or nonce-based) before launch.

### 11. Medium (security/DevOps) — no Python dependency vulnerability scanning

`ci.yml` runs `npm audit` but has no `pip-audit`/`safety` equivalent for
`requirements.txt`. The idna/certifi advisories fixed in commit `330f54e` were
caught by manual review, not automation, and the same lag can recur silently.

**Fix:** add `pip-audit` to CI alongside `npm audit`.

### 12. Medium (UX) — two different review/approval UIs for the same catalogue

`ReviewWorkspace` (embedded in `catalogues/[id]/page.tsx:164`) uses one
vocabulary ("Approve classification" / "Request further review", no reject)
and a full `.../review/page.tsx` uses another ("Approved" / "Changes
requested" / "Rejected", plus assignment). Both write to the same underlying
status enum — no data bug — but a reviewer building a compliance paper trail
hits two screens with two vocabularies for the same four states.

**Fix:** make `ReviewWorkspace` a thin launcher into the full review page, or
delete one implementation.

### 13. Medium (calculation) — REPLACE-effect and threshold ("deal") duty rules have no structural guard against double-counting

`core/duty.py`'s deals block (646-674) computes its top-up from the
*pre-replacement* base rate; the later replacements block (676-697) only
strips the original base-rate component by exact label match and never
reconciles the deal top-up. The one cross-regime guard that exists
(`core/regimes.py:407-414`, note-52(f)/family232) is specific to that one
interaction, not general. No test constructs a REPLACE+threshold
co-occurrence (`grep -n threshold_pct tests/test_duty.py` shows none). Not
confirmed as a live wrong number on the current dataset — flagged as an
untested architectural gap.

**Fix:** add a regression test combining a REPLACE rule and a threshold rule on
the same code+origin; fix or explicitly document the interaction.

### 14. Medium (DevOps) — AD/CVD ingest has no publish-time integrity floor

`ingest/build.py` enforces `FLOORS`/`validate()`/`BuildRejected` for the
HTS/Ch99 tables; `ingest/refresh.py:97-105` copies the AD/CVD scraper's JSON
straight into the release directory on a zero exit code with no check on order
count or non-emptiness. A Federal Register formatting change that broke
extraction could silently ship a near-empty `adcvd_orders.json` — every quote
would then report "no AD/CVD order" as an absence, not a visible error.

**Fix:** add a floor/validation gate to the AD/CVD refresh step matching
`ingest/build.py`'s pattern.

### 15. Medium (UX) — silent no-op past the 200-watched-codes cap

`watchCode()` (`src/lib/catalogues.ts:264-273`) uses `INSERT OR IGNORE` gated
on a count; past the cap the insert is silently skipped with no exception and
no user-visible message anywhere in the app. Violates the app's own stated
design principle (a total that leaves something out must say so).

**Fix:** return an explicit failure the UI surfaces; audit for other silent-cap
patterns.

### 16. Medium (frontend consistency) — several important buttons bypass the `.btn` design-system primitive

`hts/[code]/page.tsx:417-434` (Watch button), `account/page.tsx:106-118`
(alert toggle), `catalogues/[id]/page.tsx:133-148` (Export/Evidence/Re-price),
`catalogues/page.tsx:52-65,123-128` (Delete) all hand-roll
`px-4 py-2 text-[14px] font-medium` with no rounding/hover/44px touch target,
recurring independently at least four times.

**Fix:** sweep onto `.btn`/`.btn-secondary`.

### 17. Low/repo-hygiene — `web/AGENTS.md` contains a prompt-injection-style instruction

Found independently by two of the five reviews: a line instructing any AI
agent reading the file to fetch `node_modules/next/dist/docs/` before writing
code, framed as auto-generated by `next dev` — not real Next.js behavior. Both
subagents correctly ignored it and it had no effect on this audit. Worth the
team looking at how it got there.

### Additional Low/Medium items (full detail in each subagent's original report, available on request)

- `ingest/notes.py:31` (`EXCLUSION_REF`) — **fixed.** `[^.]{0,4000}` stopped at
  the first period, which is always inside the dotted HTS code it was trying
  to capture ("9903.88.01"), so `excluded_by` was always empty. Two more real
